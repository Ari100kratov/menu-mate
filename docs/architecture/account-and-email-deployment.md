# Учётные записи и настройка почты

## Из чего состоит почтовая инфраструктура

MenuMate не поднимает почтовый сервер в production. API формирует транзакционное письмо и передаёт его по SMTP выбранному провайдеру. Провайдер принимает письмо, подписывает его DKIM и доставляет в Яндекс Почту, Mail.ru, Rambler, Gmail и другие ящики по обычным интернет-стандартам.

Нужны четыре части:

1. адрес отправителя, например `no-reply@example.com`;
2. SMTP host, port, режим TLS, login и пароль приложения;
3. DNS-записи домена отправителя: SPF, DKIM и DMARC;
4. публичный HTTPS-адрес MenuMate для ссылки сброса пароля.

Цена зависит от провайдера. SMTP уже может входить в тариф доменной почты или хостинга, а специализированные транзакционные сервисы обычно имеют бесплатный небольшой лимит и плату при росте объёма. Сам код MenuMate и Mailpit бесплатны. Не следует разворачивать собственный интернет-почтовый сервер только ради приложения: репутация IP, обратная DNS-запись, очереди и обработка отказов потребуют значительно больше сопровождения.

## Локальная разработка

Aspire автоматически запускает Mailpit:

- SMTP: `localhost:1025` без TLS и авторизации;
- web-интерфейс: `http://localhost:8025`.

Mailpit нужен не только тестам. Он позволяет разработчику пройти регистрацию, смену email и сброс пароля без настоящего ящика, увидеть HTML и plain-text версии, проверить ссылку и убедиться, что секрет не попал в лог. Интеграционные тесты используют захватывающий `IAuthEmailSender`, потому что им важны детерминированность и отсутствие зависимости от сети; Mailpit предназначен для ручной локальной проверки.

## Переменные production

В Portainer задаются:

```dotenv
JWT_EXPIRATION_IN_MINUTES=15
ACCOUNT_ACTION_HASH_SECRET=<отдельная случайная строка не короче 32 символов>

EMAIL_ENABLED=true
EMAIL_SMTP_HOST=smtp.provider.example
EMAIL_SMTP_PORT=587
EMAIL_SMTP_SECURITY=StartTls
EMAIL_SMTP_USERNAME=no-reply@example.com
EMAIL_SMTP_PASSWORD=<пароль приложения или SMTP API key>
EMAIL_FROM_ADDRESS=no-reply@example.com
EMAIL_FROM_NAME=MenuMate

PUBLIC_WEB_BASE_URL=https://menu.example.com

LEGAL_OPERATOR_NAME=<полное имя оператора сервиса>
LEGAL_PRIVACY_CONTACT_EMAIL=privacy@example.com
LEGAL_TECHNICAL_LOG_RETENTION_DAYS=30
LEGAL_BACKUP_RETENTION_DAYS=30
```

`EMAIL_SMTP_SECURITY` принимает только `None`, `StartTls` и `SslOnConnect`. Обычная рекомендуемая комбинация провайдера — port `587` и `StartTls`; port `465` обычно использует `SslOnConnect`. `None` допустим только для локального Mailpit или доверенной внутренней сети.

`ACCOUNT_ACTION_HASH_SECRET` не должен совпадать с `JWT_SECRET`. Для генерации на Linux:

```bash
openssl rand -hex 32
```

Секрет нельзя менять без причины: уже отправленные коды и ссылки перестанут работать. SMTP-пароль и оба секрета нельзя включать в Git, логи или screenshots.

`PUBLIC_WEB_BASE_URL` задаётся вручную и не строится из входящего `Host`, поэтому письмо не может получить подменённую ссылку. В production допускается только публичный HTTPS-адрес приложения без завершающего `/`.

## DNS и доставка в российские ящики

Точные значения выдаёт почтовый провайдер. В DNS домена отправителя нужно:

- добавить один согласованный SPF record; не создавать несколько независимых SPF-записей;
- опубликовать DKIM public key с selector провайдера;
- добавить DMARC, начав с наблюдения, например `p=none`, и получать отчёты;
- после проверки доставки постепенно перейти на `quarantine` или `reject`;
- обеспечить совпадение домена `From` с доменами, прошедшими SPF/DKIM alignment.

Поддержка адресов `.ru` не требует отдельной ветки кода: SMTP и UTF-8 письма одинаковы для всех провайдеров. На практике доставляемость проверяется отдельными тестовыми адресами в Яндекс Почте, Mail.ru и Rambler, потому что их антиспам-оценка может отличаться. В заголовках полученного письма должны быть успешные результаты SPF, DKIM и DMARC; письмо не должно регулярно попадать в «Спам».

## Обновление Git-backed stack в Portainer

1. Сделать backup PostgreSQL и MinIO. Проверить возможность восстановления, а не только наличие файлов.
2. Создать адрес отправителя и SMTP credential у провайдера. При доступности использовать пароль приложения, а не пароль владельца почты.
3. Добавить перечисленные переменные в `Stacks → Environment variables`. Сверить `PUBLIC_WEB_BASE_URL` с внешним HTTPS-доменом.
4. Сохранить текущие `POSTGRES_PASSWORD`, `JWT_SECRET`, MinIO и Dashboard secrets. Не генерировать их заново при обычном обновлении.
5. Обновить Git revision стека и выполнить `Pull and redeploy` с пересборкой образов.
6. Проследить, что одноразовый контейнер `migrator` завершился с code `0`. Он добавит данные жизненного цикла аккаунта, одноразовые действия и фиксацию принятой версии политики; API стартует только после него.
7. Проверить health check API и web, затем логи API. В логах не должно быть шестизначных кодов, reset token, паролей или SMTP credential.
8. Оставить `EXPOSE_API_DOCS=false`.

Если migrator завершился ошибкой, не запускайте API вручную поверх старой схемы. Сохраните логи, исправьте конфигурацию или восстановите backup и повторите развёртывание.

## Smoke test после развёртывания

Используйте отдельные тестовые адреса и выполните по порядку:

1. зарегистрировать нового пользователя; убедиться, что до кода вход возвращает запрет и refresh cookie не создаётся;
2. подтвердить код, войти и проверить созданные стандартные приёмы пищи;
3. войти существующей учётной записью: она должна работать со статусом `LegacyUnverified`;
4. запросить подтверждение прежнего email либо сменить его через текущий пароль и код на новом адресе;
5. сменить имя и убедиться, что сессия сохранилась;
6. сменить пароль и убедиться, что приложение потребовало новый вход;
7. запросить сброс пароля, открыть HTTPS-ссылку, задать новый пароль и войти вручную;
8. проверить письмо и заголовки доставки в Яндекс Почте, Mail.ru, Rambler и одном международном ящике;
9. повторно использовать код и reset link: сервер должен отклонить их.
10. открыть без авторизации `/privacy` и `/account-deletion`, проверить реквизиты оператора и сроки;
11. проверить принятие политики существующим пользователем;
12. на отдельном тестовом аккаунте проверить удаление с неверным и верным паролем, после чего убедиться, что повторный вход невозможен.

## Что нужно перед Android-релизом

Текущая схема совместима с PWA, Trusted Web Activity и отдельным Android-клиентом: API-контракты не зависят от web-экрана, ссылки используют HTTPS, а refresh cookie защищён `HttpOnly` и `Secure`.

Реализованный контур для Google Play включает:

- удаление учётной записи из приложения и публичную web-инструкцию;
- публичную политику конфиденциальности и сроки удаления backup;
- версионируемое подтверждение политики.

Перед публикацией все еще требуется вручную:

- заполнить декларацию Data Safety по фактической production-конфигурации;
- указать HTTPS URL `/privacy` и `/account-deletion` в Google Play Console;
- заменить тестовые реквизиты оператора и провести юридическую проверку текста;
- при нативной обработке ссылок — Android App Links, `assetlinks.json` и безопасная передача reset token экрану приложения.
